# 电商选品 MCP —— 产品化设计文档

> 目标：把"自用工程"改造成**真正的多用户产品**——每个用户用自己的京东/淘宝账号、在自己电脑上跑 worker，你只提供调度服务器。Mac 和 Windows 都要能跑。
> 本文档只描述现状、问题和改法，**不含已实施代码**。经确认后再分步实施。
>
> 状态：草案 v2（已按"多用户 + 各用各账号 + 各自跑 worker + 跨平台"重写），待确认
> 撰写：Claude Code，2026-06-13

---

## 0. 定位与铁律

**定位**：用户在自己的 Agent 客户端（已配好多模态模型）里接入这个 MCP，用**自己的**京东/淘宝账号、在**自己的**电脑上，由 AI 自动跑选品。没有 App、没有安装包，就是一个 MCP 服务 + 一个本机 worker。

**两条铁律（不变）**：
- 脚本只做机械动作（开浏览器、点击、抓取、存库、导出）。
- 判断全归 AI（淘宝关键词、同款复核、利润核算、策略取舍）。
- 补充铁律：**视觉同款复核用调用方 Agent 自己的多模态能力看截图，绝不绑定任何特定视觉 MCP**（脚本只负责截图存盘给路径）。

## 1. 最终架构（已与用户确认）

```
用户A的Agent客户端 ─┐                               ┌─ 用户A电脑: local-worker → 自己的Chrome(自己的京东/淘宝号)
                    │  HTTP + 各自 API Key           │
用户B的Agent客户端 ─┼─→  你的调度服务器  ────────────┼─ 用户B电脑: local-worker → 自己的Chrome(自己的号)
                    │   (http-server.mjs)            │
用户C的Agent客户端 ─┘   只排队/分发/收结果，不碰Chrome └─ 用户C电脑: local-worker → 自己的Chrome(自己的号)
```

**职责划分**：
- **调度服务器（你跑一台）**：收 Agent 的 `tools/call` → 按 userId 入队 → 分发给该用户的 worker → 收结果回传。**不开浏览器、不碰任何账号**。
- **local-worker（每个用户在自己电脑跑）**：长轮询领任务 → 真正开 Chrome 操作**自己的**账号 → 回传结果。**这是跨平台的战场。**
- **Agent 客户端（用户自备）**：用户自己的多模态模型，负责出关键词、看截图判同款、算利润。

**关键约束**：京东/淘宝登录态绑死在"那台跑 worker 的电脑的 Chrome"里。所以账号天然"各用各的、各自在本机"，这正是选"多用户 + 各自 worker"架构的根本原因。

## 2. 现状盘点：已有什么、缺什么

### 2.1 已经实现的（代码实锤，可复用）

- **调度服务器骨架** `mcp/http-server.mjs`：
  - `executionMode=worker` 时，把 `tools/call` 按 userId 入队、分发、收结果（`enqueueWorkerToolCall` / `handleWorkerPoll` / `handleWorkerResult`）。
  - 多用户鉴权：每个用户一对 `apiKey`（Agent 用）+ `workerKey`（worker 用），`loadUsers` 从 `ECOMMERCE_SOURCING_USERS` 读取。
  - 任务超时（30 分钟）、worker 领取超时（30 秒）、worker 在线监控（`workerHealthSummary`）。
- **local-worker 骨架** `mcp/local-worker.mjs`：长轮询领任务、执行、回传，带 workerId。
- **本机直连模式** `mcp/server.mjs`：stdio MCP，适合"单用户在自己电脑直接用"（不经服务器）。
- **选品全链路**：账号池 + 冷却轮换 + jd/taobao harvest + 审核包 + 入库 + 导出（这部分成熟）。

### 2.2 缺的 / 坏的（要改）

| 类别 | 问题 | 严重度 |
|---|---|---|
| **跨平台** | worker 开/管 Chrome 只认 macOS，Windows 全裂 | ⚠️ 最高 |
| **私人数据** | 代码里有你的真实账号 UUID、旧 App 名、私人路径 | 高（隐私+割裂） |
| **worker 安装** | 只有 Mac 的 `install-worker.sh`，Windows 用户没法装 | 高 |
| **傻瓜引导** | 加账号/扫码/体检没串成人话流 | 中 |
| **多用户运维** | 发 Key、服务器常驻、worker 在线提示，骨架有但不完善 | 中 |

## 3. 问题 A：跨平台 worker（最硬，核心瓶颈）

**现状（代码实锤 `lib/chrome.js`）：**

| 位置 | 现状 | Windows 后果 |
|---|---|---|
| `chrome.js:218` | Chrome 路径写死 `/Applications/Google Chrome.app/...` | 找不到 Chrome |
| `chrome.js:226` | Windows 分支仅 `chrome.exe`（无完整路径） | 默认装在 `C:\Program Files\Google\Chrome\` 下，找不到 |
| `chrome.js:145/150/178` | 多处 `if (process.platform !== "darwin") return` | "检测已开 Chrome / 防重复开窗"在 Win 整段失效 |
| `chrome.js:163` | `/bin/ps` 查进程 | Windows 没有 `ps` |
| `chrome.js:199` | `/bin/kill` 关进程 | Windows 没有 `kill` |
| `ai-controller.js:355` | 已正确区分 `Meta+A`/`Control+A` | 这处 OK |

**改法：抽出"平台适配层"**，把和操作系统相关的四件事抽成统一接口，mac/windows 各一份实现：
1. **找 Chrome**：mac 查 `/Applications` + `mdfind`；windows 查注册表 `HKLM\...\App Paths\chrome.exe` + 默认安装路径（`Program Files` / `Program Files (x86)` / `LocalAppData`）。找不到都给"去这里下载 Chrome"的人话指引。
2. **开 Chrome**：两端都用 `--remote-debugging-port` + `--user-data-dir`，只是可执行文件路径不同。
3. **查进程/端口**：mac 用 `ps`；windows 用 PowerShell（`Get-CimInstance Win32_Process` 读命令行）或 `wmic`。
4. **关进程**：mac 用 `kill`；windows 用 `taskkill /PID`。

**验证**：你有 Windows 机器，可在真实环境实测 worker 开 Chrome、扫码、跑一个 harvest。这是这块能落地的前提，已具备。

## 4. 问题 B：剥离私人数据

**现状**：
- `accounts.js:10-14` `KNOWN_ACCOUNTS` 硬编码你三个真实账号 UUID。
- `accounts.js:7` 旧 App 名 `电商选品智能体` + `Library/Application Support/...` 私人路径。

**澄清**：这不是"绑死别人没法用"——新用户走 `account_add`（`accounts.js:82`）就能加自己的号，根本不碰 KNOWN_ACCOUNTS。它对新用户是**死代码 + 隐私泄漏**，且造成"老用户自动发现 / 新用户手动添加"两条路割裂。

**改法**：
1. 删 `KNOWN_ACCOUNTS` 真实 UUID（给你留一个 git 忽略的本地迁移文件，平滑过渡你自己的旧账号）。
2. 去掉旧 App 名和私人路径，数据目录统一收口到 `~/.ecommerce-sourcing-agent`（已有此常量）。
3. 账号池一律从空开始，新老用户都走 `account_add`，逻辑归一。

## 5. 问题 C：普通用户怎么在自己电脑跑起 worker（傻瓜化）

**难点**：目标用户"完全不懂技术"，却要在自己电脑：装 Node → 跑常驻 `local-worker` → 扫码登录自己的号。这是整个产品最大的上手门槛。

**改法（分两层）**：

**5.1 降低安装门槛**
- Mac：保留并完善 `install-worker.sh`（自动装依赖、写好启动项）。
- Windows：新增对应的安装方式（`.ps1` PowerShell 脚本或 `.bat`），做到双击/一条命令把 worker 跑起来并设为开机自启（可选）。
- worker 启动参数（服务器地址、workerKey）做成引导式：用户从你那拿到一串"接入码"，填一次即可。

**5.2 接入后全程对话驱动**（worker 在线后，用户只在 Agent 里说人话）

```
用户：把选品工具准备好
AI（bootstrap）：环境正常 ✅ 找到 Chrome ✅。你有几个京东号、几个淘宝号？
用户：京东两个，淘宝一个
AI（account_add ×3 + account_login）：已打开京东登录页，请用手机扫码，好了告诉我。
用户：好了
AI（account_check）：京东账号一就绪 ✅ …（依次完成）全部就绪，可以开跑。
```

**自愈话术**（错误不甩给用户）：封控→自动暂停+冷却+换号并说人话；全冷却→告知恢复时间；登录失效→提示重新扫码并自动开登录页；找不到 Chrome→给下载链接。

## 6. 问题 D：多用户运维（你的服务器侧）

**现状**：骨架已有（`loadUsers`、API Key/Worker Key 双钥、按 userId 派发、worker 健康监控）。

**改法（补完）**：
1. **发 Key 流程**：给每个用户生成一对 `apiKey + workerKey`，整理成"用户拿去填 Agent 客户端 / 填 worker"的两段配置。
2. **服务器常驻**：进程守护（pm2 / systemd / Windows 服务），崩溃自启。
3. **可观测**：每个用户的 worker 是否在线、队列多长、最近任务成败，`/health` `/users` 已有雏形，补一个简单状态页或日志。
4. **安全**：服务器对外时强制 API Key（代码已要求非本机监听必须配 Key，`http-server.mjs:30`）；建议加 HTTPS（放到反向代理后面）。
5. **隔离**：确认每个用户的选品数据库/账号池互不串（worker 在各自电脑上跑，数据天然隔离；服务器侧只按 userId 路由任务，不存业务数据）。

## 7. 实施分步（单机 + 多用户一起做，按依赖排序）

> 全程：守铁律；每步配测试 + typecheck 绿；不碰用户登录态和选品数据。

**阶段一：清理与归一（风险低，先做）**
1. 剥离私人数据（KNOWN_ACCOUNTS / 旧 App 名 / 私人路径 → 统一数据目录）。
2. 账号池统一走 `account_add`，删除老用户专用的"自动发现"路径（留本地迁移文件）。

**阶段二：跨平台 worker（最硬，核心）**
3. 抽出平台适配层（找/开/查/关 Chrome 四件事，mac + windows 各一份）。
4. Windows 用注册表/默认路径找 Chrome、PowerShell/`taskkill` 管进程。
5. **在你的 Windows 机器实测**：worker 开 Chrome → 扫码 → 跑一个 harvest 全通。

**阶段三：worker 安装与引导（傻瓜化）**
6. Windows 安装脚本（`.ps1`/`.bat`），Mac 脚本完善；接入码引导。
7. `bootstrap` 升级为环境体检 + 加账号一键化 + 自愈话术。

**阶段四：多用户调度层（建立在单机能跑通之上）**
8. 发 Key 流程 + 两段配置产出。
9. 服务器进程守护 + 状态可观测 + 安全（API Key/HTTPS）。
10. 端到端：两个不同用户、各自 worker、各自账号，经你服务器并行跑通。

---

## 8. 风险与前置条件

- **跨平台是大头**：阶段二工程量最大，但你有 Win 机器可实测，风险可控。
- **worker 常驻对小白仍是门槛**：即便脚本一键化，"电脑上常年跑一个后台程序"对完全不懂的人仍需一次性协助（你或代配）。这是架构决定的，绕不开。
- **风控天花板**：这是现实约束，不是代码能根治——多用户各自账号反而分散了单账号压力，比集中跑更安全，这点架构上是有利的。
- **服务器是你的成本与责任**：常驻、带宽、稳定性、用户 Key 管理都在你这。

2. **KNOWN_ACCOUNTS 你的旧账号**：直接删（之后重新 account_add），还是留本地迁移文件？
3. **worker 自启**：要不要做成开机自启的后台服务？还是用户每次自己点一下启动？
4. **服务器部署形态**：你打算把调度服务器跑在哪（自己电脑/云服务器）？这影响 HTTPS、域名、守护方式怎么写。
5. **第一个里程碑**：把"单个用户在自己 Windows 电脑上，经你服务器跑通一个选品"定为第一个可验证里程碑，可以吗？
